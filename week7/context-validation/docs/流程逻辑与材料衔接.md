# 流程逻辑与材料衔接

## 1. 从既有梳理到当前实现

本节沿用已有“接收材料—查找依赖—选择上下文—填充—验证—维护”的主线，将每一步对应到当前文件。原始逻辑材料为本地`experiments/004-context-workflow/上下文系统利用方案_人工与智能体职责.md`、`prototypes/context-account/上下文收集与维护方案.md`及其`source/大概流程_原始快照.md`。这里只迁入通用流程；早期样例的函数名称、异常类型和测试数量不作为当前输入。

|步骤|要解决的问题|当前实现/文档|交接条件|

## 2. 用当前连续操作测试串联

阅读`testSequence()`时，不能只看方法最后的余额断言。先确认字段与`setUp()`，再进入`prepareSequence()`，逐项追踪存款、取款和辅助方法中的两次断言，最后回到目标方法检查后续取款及最终断言。

在selection中选择字段、准备、helper及相应业务定义，并用reason说明其关系；export验证这些定义的来源；人工再按R3—R5检查状态演化和断言顺序。这样，选择文件、上下文输出和测试意图形成同一条证据链，而不只是互不关联的文件列表。

余额不足样例同理：异常类型、异常包围的操作、异常后的余额检查及后续合法操作分别复核。参数和值应从当前冻结源码读取，不能套用早期案例。

## 3. 反馈与维护的实现边界

源码变化后导出器会拒绝旧索引；这是摘要失效检测，不是完整的反向依赖分析。当前尚无自动“变更成员→受影响测试”维护器，也不自动生成修复候选。应重新索引，人工核对相关选择，保存新版本，再将诊断交回对应步骤。

完整类、独立选择、实际输入快照和执行报告应共同保留。研究不同上下文策略时还需固定模型、预算与允许读取范围；当前账户样例适合流程核对，不能据此推断性能或质量提升。

## 4. 与hzy-week7文档组织的对应

参考其公共材料工具README与实现记录的组织方式：区分程序与智能体职责；给出可复制任务、具体命令及输出文件；将事实、推断和待确认项分开；说明版本失效与错误处置。这里复用文档方法，不将其JavaParser/SymbolSolver、SQLite、分页查询或材料合并等实现能力记为当前工具已有功能。
