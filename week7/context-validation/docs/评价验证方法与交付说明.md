# 可执行性评价方法与交付说明

## 1 当前环节与评价问题

项目流程为：理解Java测试 → 准备上下文与目标接口 → 生成仓颉测试 → 验证与修复 → 分析案例。本模块处于验证阶段，检查候选测试是否具有最基本的运行条件。

需要分别回答三个问题：给定代码是否编译成功；预期测试究竟执行了多少；在已核验的正常业务实现上，执行结果是什么。编译成功、退出码为0或者终端显示success，都不能代替这三个问题的逐项核对。

统计单位有两个：编译按“业务实现＋测试代码＋配置”组合统计；执行按测试方法统计。批量运行中的诊断用例不混入正常业务实现的通过情况。

## 2 运行前先核验材料

提交人先确认正常业务实现满足明确约定，参考测试的输入、准备、调用和断言与原要求一致。仓颉测试不是因为运行通过就自动成为参考答案。正常实现、参考测试的核验要结合源代码、对应Java行为和已有对照记录。

本次账户材料来自已保存的004开发实验，核验路径为：Java与仓颉正常版本的两条测试均通过；对应的“减法改加法”和“先扣款再抛异常”版本分别触发预期失败。历史材料位于项目experiments/004-context-workflow/runs/2026-10-28-r01。本轮另行保存实际输入和快照，避免日志与源码版本错配。

这些账户材料用于开发验证流程，当前智能体已见过参考实现，不能作为盲测翻译准确率的数据。最终业务约定和参考测试仍需提交人复核确认。若材料本身有误，单独记录材料问题，不直接归因为译文错误。

## 3 方法步骤

| 步骤 | 程序工作 | 人工职责与检查点 |
| --- | --- | --- |
| 登记组合 | 读取业务、测试、预期清单和工具链 | 固定版本；优先填写方法清单；指定normal或diagnostic用途 |
| 收集文件 | 收集.cj、排除构建目录，复制到独立工作目录并保存SHA256 | 确认全部必要源文件已提供，依赖和资源不缺失 |
| 编译 | 单独运行cjc --test，保存命令、输出、退出码 | 区分源代码错误、依赖缺失和环境问题 |
| 测试发现 | 使用--dry-run取得发现总数及可解析名称 | 核对名称；发现0项不能算成功；跳过项缺少名称时保留缺口 |
| 实际执行 | 输出XML并与终端完整汇总交叉核对 | 确认过滤选项符合目的，没有遗漏预期测试 |
| 评价 | 计算执行比例和通过情况，生成状态 | 查看异常分类，不能只读一个通过率 |
| 留档 | 保存配置、环境摘要、源码快照、日志、JSON/CSV/Markdown | 复核后注明负责人；修复必须新建运行目录 |

当前编译后端直接调用cjc，而不是cjpm。这样能把编译失败与测试执行失败分开。单包且不依赖外部构建的示例适用；需要完整cjpm依赖解析的项目应另扩展后端。

## 4 指标与分母

| 指标 | 定义 | 未完成时怎样处理 |
| --- | --- | --- |
| 编译成功率 | 编译成功组合数／实际尝试编译组合数 | 输入缺失与环境准备失败不进入此分母；另报全部组合数 |
| 预期测试执行比例（清单模式） | 实际执行且属于预期清单的方法数／预期方法数 | 编译、发现或执行结果不完整时为null；明确零执行时为0 |
| 数量执行比例（仅数量模式） | 实际执行数／预期数量 | 不能证明执行的是正确方法；数量不符单独判定，比例可能超过1 |
| 已执行测试通过率 | 通过数／实际执行数 | 执行数0时为null，避免0/0被写成100% |
| 预期测试通过比例 | 预期方法中通过数／预期数；数量模式用通过数／预期数 | 与“执行了多少”分开读 |
| 正常组合完整通过率 | business_role=normal且状态PASSED的组合数／全部normal组合数 | 包含正常组合的材料或环境失败，因此属于整体可用性；不是纯断言通过率 |

实际执行数=通过数＋断言失败数＋测试错误数；跳过不计执行。部分执行可以得到“已执行部分全通过”，但仍因预期清单不完整而不能判定整个组合通过。

本次最终批量记录：13组输入，12组进入编译，11组编译成功；编译成功率11/12。唯一normal组合有2条预期测试，2条实际执行、2条通过，正常组合完整通过率1/1。其余为工具诊断材料。这些数值不能报告成模型翻译成功率。

## 5 怎样判定结果

按阶段先后处理失败。未取得可信运行报告时保留未知数量，不猜测为0；取得完整报告后先检查一致性，再判断零执行、测试错误、断言失败和清单遗漏。状态只表示主要结果，详细数量、退出码、未执行清单与日志同时保留。

未预期异常为TEST_ERROR；断言比较失败为ASSERTION_FAILED；进程无法启动、报告丢失或非正常退出另列运行异常。若编译器拒绝源代码，状态为COMPILE_FAILED。环境初始化失败为ENVIRONMENT_ERROR，输入路径缺失为INVALID_INPUT。

发现阶段可能无法列出静态跳过项的名称。本次1.2.0实测中，发现输出只给跳过总数，而运行XML补齐了该项名称。脚本分别记录两个阶段的身份信息是否完整，不把发现阶段的未知名称写成“此方法不存在”。若运行后仍无法确认，则保留未解析条目。

## 6 验证脚本本身是否可靠

先准备可以人工解释结果的小输入，覆盖正确运行、断言失败、意外异常、编译错误、零测试、跳过、过滤遗漏、错误清单、缺失文件、数量模式、第二个不同样例和超时。再补环境缺失与数量不符两种专项输入。

验收按事先设计的分类检查真实运行记录，并交叉检查JSON、CSV、Markdown与源码哈希。没有通过修改期望值来让失败场景变为成功。调试时暴露出的跳过项发现格式问题保留在第一轮记录中，修复后重新运行批量验收。

## 7 能支持的结论与限制

本模块可证明：这些版本的源文件在已记录环境中能否编译、发现和执行，是否遗漏预期清单，以及正常实现上的结果。它不能独立证明Java与仓颉测试语义等价，也不能证明对全部业务错误都有检测能力。

下一层验证应结合测试意图核验和经过核对的错误实现。这里的错误实现只是检验执行脚本能否识别失败，尚未形成全面的错误实现生成工具或语义评价体系。缺少目标业务实现时，可用骨架检查类型与组织，但不能把骨架编译通过当作真实业务验证。
