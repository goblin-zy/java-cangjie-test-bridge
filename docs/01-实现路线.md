# 实现路线：从一条 Java 测试走到可执行性报告

## 基本概念

“上下文”是解释一条测试所需的额外代码，例如账户字段、测试前准备、辅助断言、被调用的业务方法及异常类型。“成员索引”是这些声明的位置与标识清单。“快照”是本次源文件的冻结副本，哈希用于发现之后的改动。“参考测试”是已有参考实现，不属于本工具生成的翻译结果。

## 任务一：上下文查找工具

1. `context_lookup.py index` 调用已有 `JavaTestSkeletonExtractor.java`，分别分析 Java 测试和业务目录，保留原成员 ID 和 UTF-16 源码位置，生成 `catalog.json`、`index.md` 与源文件快照。
2. 人或智能体编辑 `examples/account/selection.json`：`target` 指定目标测试，`evidence` 逐项指定依赖；`group` 区分测试/业务来源，`symbol` 是带所属类型的签名，`reason` 和 `use` 解释为什么选、怎么用。
3. `export` 根据选择查找真实成员，检查现场源码和快照哈希，按原位置取出代码，生成 `context_01..03.json/md`、冻结的选择文件和 `checks.json`。
4. 普通取款重点看被调用接口；连续操作重点看准备与辅助方法中的中间断言；余额不足重点看异常类型及异常后账户是否仍可正常操作。示例选择的证据条目为10、12、10，共32条核对。

导出成功仅说明所选片段真实且可追溯。漏选一个真实依赖仍可能导出成功；完整测试类也可能间接保留该代码。因此当前输出不是自动完整依赖分析，不能据此判断翻译质量。

## 任务二：可行性验证方法执行

1. `evaluate_account.py` 固定九条参考测试方法，读取仓颉业务/测试文件，记录编译器与运行库哈希，生成配置。
2. `cangjie_runner.py` 先检查环境和输入，再编译测试，发现测试清单，执行测试并解析控制台/XML结果。
3. 将预期清单、发现清单和实际执行清单相互核对。只看进程退出码或“0失败”会漏掉零测试、过滤遗漏和跳过等情况。
4. 报告保留每阶段命令、输出、退出状态、源码快照与哈希；JSON用于程序读取，CSV用于汇总，Markdown用于人工查看。

历史故障场景用于检查执行器能否正确分类错误。当前九条账户参考测试用于检查既有材料是否能在记录环境执行。这两组数据不能混算成翻译准确率。可执行性是本周可行性验证的实际落地部分，语义一致性仍需后续核验。

## 任务三：论文方法与本项目的关系

ReCodeAgent 将分析、规划、翻译、验证组织成有反馈的流程。我们借鉴“源码证据支撑上下文”和“失败报告驱动修复”的思路；当前工具仍是局部基础设施，没有实现论文完整智能体工作流。阅读时重点检查断言是否保留：测试通过可能来自正确翻译，也可能来自删掉测试要求，两者必须区分。

所有具体命令、参数和预期输出见[逐步教程](../week7/context-validation/docs/使用教程.md)。
