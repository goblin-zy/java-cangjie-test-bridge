# 仓颉错误业务实现构造提示词与使用说明

版本：1.0（固定输出结构版）  
整理日期：2026-10-26

## 简单使用说明

**用途：** 根据仓颉业务代码和对应测试，指导 AI 构造独立的错误业务版本，供后续评价测试的错误检测能力。生成结果不代表已经通过编译或已经被测试检出。

1. 复制下方“提示词正文”的全部内容，从“请根据我提供的……”开始，直到文末，交给 AI。
2. 在输入区填入业务代码和对应测试代码；多文件注明原项目相对路径。AI 能访问本地项目时，也可以提供项目及文件路径，并确保其能实际读取。若提供仓库链接，应允许 AI 读取，并尽量固定提交版本。
3. “可选补充要求”可以留空，无需另写接口约定、测试意图或错误数量。需要落盘时，可在此指定输出目录。
4. 检查输出的错误清单、各版本业务文件和补丁。后续使用时，每次从原始项目独立替换一个版本的文件，或应用一个补丁；两种方式二选一，不叠加多个版本。

默认首批最多12个版本，实际数量由 AI 根据有效候选决定。每个版本包含完整修改文件、补丁和 JSON 说明，批次另附 Markdown／JSON 总清单、生成记录及静态核对记录。只有对话输出能力的 AI 应逐文件展示内容，不得假称已经保存。

**注意：** 固定目录和 JSON 字段用于提高输出一致性，仍需核对实际文件与清单是否匹配。旧批次不会因本提示词更新而自动符合新格式。本提示词默认不执行编译、测试或对照实验。

## 提示词正文

请根据我提供的**仓颉业务代码和对应的仓颉测试代码**，生成一批彼此独立的错误业务实现，供后续比较不同测试的错误检测能力。

本任务只构造错误实现、说明依据并整理文件。不修改测试，不开展对照实验，不计算评价指标。

### 一、输入

#### 仓颉业务代码
【粘贴代码；多文件分别标明路径，也可以提供可访问的项目路径】

#### 对应的仓颉测试代码
【粘贴测试代码；多文件分别标明路径，也可以提供可访问的文件路径】

#### 可选补充要求
【可以留空，例如输出位置、关注模块、错误类别或数量】

除业务代码和测试代码外，不要求我另行整理接口约定、测试意图或生成数量。没有补充要求时，按以下默认规则工作。

### 二、分析与错误选择

阅读业务代码和测试代码，必要时查阅输入项目范围内的相关定义，识别：

- 初始化状态、输入、被测对象及接口。
- 关键操作和调用顺序。
- 全部断言，包括辅助方法中的检查。
- 异常触发条件、异常类型和异常后的状态检查。
- 与上述检查相关的业务分支、计算、返回值和状态变化。

根据源码、测试和已有注释判断预期行为，不只凭名称猜测业务规则，也不把原实现的每个细节都视为正确约定。

存在代码与测试冲突、依赖缺失或行为不明时，记录疑点，避开缺乏依据的修改。局部信息不足时继续处理其他可靠部分；整体无法判断时说明原因，不编造结果。

从以下角度选择适用的错误：

1. 边界判断。
2. 计算与返回值。
3. 状态更新。
4. 异常条件与类型。
5. 会影响行为的关键操作顺序。

默认选择规则：

- 按“被测操作＋被检查行为”识别独立检查点，不机械地按断言数量划分。
- 优先为不同检查点各选一个修改小、行为差异明确的错误。
- 同一检查点可补充不同错误机制；仅更换常量而产生基本相同偏差的候选，通常只保留一个。
- 兼顾不同方法、分支和适用类别，不机械覆盖全部类别。
- 默认首批最多生成12个有效版本，不要求达到上限。
- 候选重复、可能没有行为差异、依据不足或必须破坏接口时，停止生成。
- 可靠候选超过上限时，优先保留检查点覆盖更广、错误机制更多样的版本。
- 简要说明实际数量和选择依据，不为凑数制造错误。

优先选择与现有测试检查范围相关的错误。若保留了有明确行为依据、但现有测试可能无法发现的错误，须明确标为“预测未检出”或“待确认”。

### 三、修改约束

1. 每个版本都从同一份原始业务代码独立修改，不叠加其他版本的错误。
2. 每个版本只植入一个独立业务错误机制。必要的多行修改和同一错误导致的多个后果，不自动视为多个错误。
3. 尽量保持原接口，保留测试调用所依赖的类型、名称、参数、返回类型及可见性。仅在必要时调整相关内部实现和辅助代码。
4. 不修改测试、断言、预期值、初始化或测试辅助代码。
5. 保持原有项目结构、依赖及构建条件，沿用输入中的仓颉写法。
6. 不通过语法错误、未定义符号、类型不匹配、缺失依赖或破坏接口制造失败。
7. 不用直接终止程序、无意义崩溃或无限循环代替业务错误。
8. 不夹带无关重构、格式调整或批量改名。
9. 每个错误都须有明确触发条件，并能解释正常与错误行为的差别。
10. 不编写识别测试名称、测试环境或测试数据的特殊逻辑。

### 四、固定输出目录

除非我明确要求调整，否则使用以下结构，不随意更换目录名或文件名：

```text
<批次目录>/
├─ original/
│  ├─ <业务文件原相对路径>
│  └─ <测试文件原相对路径>
├─ mutants/
│  ├─ M001/
│  │  ├─ <修改后的业务文件原相对路径>
│  │  ├─ change.patch
│  │  └─ 错误说明.json
│  ├─ M002/
│  │  └─ ……相同结构
│  └─ ……
├─ 错误清单.md
├─ 错误清单.json
├─ 生成记录.json
└─ 静态核对.json
```

以 Account 材料为例，业务文件路径为：

```text
original/cangjie/src/account.cj
original/cangjie/src/account_test.cj
mutants/M001/cangjie/src/account.cj
```

具体规则：

- 有原项目相对路径时保留原路径；只有文件名时使用文件名，不猜测原目录。
- 相对路径不得包含盘符、绝对路径或越出批次目录的 `..`。
- 批次目录默认命名为 `<业务模块>-<YYYYMMDD>-001`，例如 `account-20261026-001`。发生重名时递增序号，不覆盖已有批次。
- 错误版本从 `M001` 连续编号，不预先创建空版本目录。
- `original/` 保存本次实际使用的原始业务、测试及必要辅助输入，内容保持不变。
- 每个错误目录保存该版本修改涉及的完整业务文件，以及对应补丁。未修改文件复用原始版本，不必重复复制。
- 不把测试复制进各错误目录，不生成修改后的测试。
- `change.patch` 始终相对于同一份原始代码，使用 `a/<相对路径>` 和 `b/<相对路径>`。
- 完整业务文件与补丁表达同一份修改，使用时二选一，不重复应用。
- 有文件写入能力时实际创建上述文件；没有时按相同路径逐文件输出完整内容，不声称已经保存。
- 实际生成文件后，提供同名 ZIP 压缩包。无法打包时说明原因，不虚构下载链接。
- 不额外生成无关文档或临时代码文件。

### 五、固定 JSON 格式

所有 JSON 使用 UTF-8、合法语法，统一设置：

```json
"schema_version": "1.0"
```

以下字段名称和类型固定，不自行改名或省略。未知字符串、数值使用 `null`；列表使用数组，没有记录时为 `[]`。不得用虚构信息填满字段。

#### 1．每个版本的“错误说明.json”

统一使用以下结构：

```json
{
  "schema_version": "1.0",
  "id": "M001",
  "category": "边界判断",
  "summary": "错误的简明含义",
  "changes": [
    {
      "file": "业务文件相对路径",
      "member": "所属类或函数",
      "original_start_line": null,
      "original_end_line": null,
      "before": "修改前的完整相关片段",
      "after": "修改后的完整相关片段"
    }
  ],
  "expected_behavior": "有依据的正常行为",
  "basis": [
    {
      "file": "依据文件相对路径",
      "member": "测试或业务成员标识",
      "start_line": null,
      "end_line": null,
      "code": "支持判断的实际代码或注释",
      "reason": "该依据说明了什么"
    }
  ],
  "trigger": {
    "initial_state": "触发前的状态",
    "input": "具体输入",
    "operations": ["必要操作"],
    "normal_behavior": "正常版本的行为",
    "mutant_behavior": "错误版本的行为"
  },
  "related_tests": [
    {
      "id": "源码中已有的用例编号，没有则为null",
      "file": "测试文件相对路径",
      "member": "实际测试成员标识",
      "prediction": "预测检出",
      "reason": "预计由什么检查发现什么偏差"
    }
  ],
  "build_status": "未执行",
  "test_status": "未执行",
  "artifact_files": ["该版本完整业务文件相对于批次目录的路径"],
  "patch_file": "mutants/M001/change.patch",
  "unresolved": []
}
```

字段约定：

- `category` 从“边界判断、计算与返回值、状态更新、异常条件与类型、操作顺序”中选择一个主要类别。
- `changes` 可有多项，但必须共同服务于一个独立错误机制。
- 行号统一指原始输入文件，只有准确确定时才填写。
- `related_tests[].prediction` 只能为“预测检出、预测未检出、待确认”。
- 测试标识必须来自实际输入，不能编造编号。
- 没有可靠关联测试时使用空数组，并在 `unresolved` 中说明。
- 正常行为与错误行为的描述均为静态推断，不代表已经执行。
- 默认不构建、不运行测试，因此两个状态字段均为“未执行”。

#### 2．“错误清单.json”

```json
{
  "schema_version": "1.0",
  "generation_id": "批次目录名称",
  "mutant_count": 1,
  "mutants": []
}
```

`mutants` 按编号顺序包含各份“错误说明.json”的完整对象，内容必须一致，不另造一套字段。`mutant_count` 必须与实际版本数量相符。

#### 3．“生成记录.json”

```json
{
  "schema_version": "1.0",
  "generation_id": "批次目录名称",
  "created_at": null,
  "source": {
    "repository_url": null,
    "ref": null,
    "commit": null
  },
  "input_files": [
    {
      "path": "原项目相对路径",
      "role": "business",
      "snapshot_file": "original下对应文件的相对批次路径",
      "sha256": null
    }
  ],
  "requested_options": {},
  "selection": {
    "default_max_mutants": 12,
    "actual_count": 1,
    "reason": "数量和候选选择依据",
    "not_exhaustive": true
  },
  "unresolved": []
}
```

- `role` 只能为 `business`、`test` 或 `context`。
- 仓库地址、提交、时间和哈希仅填写实际可确认的信息。
- 不联网也能使用本提示词，不强制要求输入来自仓库。
- 不把静态构造过程描述为调用过其他模型的实验记录。
- `requested_options` 只记录用户实际提出的可选要求，没有则为 `{}`。

#### 4．“静态核对.json”

```json
{
  "schema_version": "1.0",
  "generation_id": "批次目录名称",
  "checks": [
    {
      "scope": "batch",
      "name": "核对项目",
      "status": "未执行",
      "evidence": null
    }
  ],
  "build_executed": false,
  "tests_executed": false
}
```

- `scope` 使用 `batch` 或对应版本编号。
- `status` 只能为“通过、未通过、未执行、受阻”。
- `evidence` 写实际核对方式和结果，不仅写“已检查”。
- 至少记录：原始快照一致性、各版本独立修改、接口声明保留、补丁与完整文件一致、JSON格式与清单一致性。
- 有适用工具时，可额外执行补丁可应用性检查和文件哈希核对。
- 没有工具或未实际检查时，如实标为“未执行”或“受阻”。
- 静态核对不替代编译、测试或完整的语义验证。

### 六、“错误清单.md”的固定内容

该文件面向人工阅读，按以下顺序组织：

1. **生成概况**：输入来源、已确认版本、主要检查点、实际数量和选择依据。
2. **文件结构与使用方式**：说明每次只选一个错误版本，从原始项目单独替换文件或应用补丁；快照目录不一定是完整项目。
3. **错误总表**：编号、类别、错误含义、修改位置、触发条件、正常与错误行为差异、预计关联测试。
4. **预测说明**：补充异常退出、断言偏差、预计未检出等需要解释的情况。
5. **静态核对与限制**：实际进行了哪些检查，哪些未执行，以及待确认问题。

Markdown 中的事实、数量和预测必须与 JSON 一致，不另外维护相矛盾的描述。

### 七、输出前核对

逐个确认：

- 从原始代码独立修改，没有错误叠加。
- 只有一个独立错误机制，具有明确触发条件和行为差异。
- 未修改测试，未明显破坏接口和构建条件。
- 完整文件与补丁内容一致。
- 版本目录、编号、路径、单项说明和总清单一一对应。
- 所有 JSON 格式合法、必填字段齐全、字段类型一致。
- Markdown 与 JSON 的数量、依据、预测一致。
- 没有把未知信息或未执行检查写成已确认结果。

不合格候选应修正或删除，不为达到数量上限保留。

本任务默认仅做静态分析与文件生成，不执行编译或测试。所有预计检测结论必须明确为预测，不得声称“已编译通过”“测试已失败”或“已经验证可检出”。

材料充分时直接开始，不要求我额外整理接口约定、测试意图或指定错误数量。最终简要报告生成数量、输出位置、已完成的静态检查及未验证事项，并提供错误清单和压缩包链接；仅能在对话中交付时，完整输出各文件并说明没有实际保存。
