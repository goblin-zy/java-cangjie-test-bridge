# 翻译材料与验证方法：规则映射、项目约定生成工具、错误实现提示词

本目录包含第七周的三部分工作：**规则映射、项目约定与公共材料生成工具、验证方法3的错误实现构造提示词及样例**，分别服务于测试翻译的材料准备和错误检测能力评价。

## 2. 规则映射

为 Java 测试及必要测试辅助代码提供仓颉转换参考，重点保留初始化、接口调用、断言、异常预期和清理行为。

- **`translation_rules.json`**：保存转换方案、适用条件、依赖、示例、语义要求、来源和核验状态，供程序或模型读取。
- **`translation_rules.md`**：解释规则分类、选择方法、覆盖范围及限制，适合先阅读。

当前版本为 **0.2.0**，包含十二类目录、21 条当前规则和3项后续候选。默认参考 Java 17、JUnit Jupiter 5.13.4、仓颉及标准库 1.2.0，使用时需确认实际项目版本。

规则库是翻译参考材料，不是自动转换器。应按当前测试选取适用规则；目标业务接口及项目专有约定由项目材料提供。

## 3. 项目约定与公共材料生成工具

将 Java 项目、已有仓颉业务代码、配置和相关文档整理为带来源的公共材料，帮助翻译后的测试正确接入目标项目。

**主要分工：**

- 本地程序负责文件扫描、源码解析、快照与索引、对应候选、证据包、检查和导出。
- Codex 根据固定提示词分析证据，整理接口对应、公共约定、可复用代码及缺失或冲突事项。程序内部不直接调用模型 API。

**基本流程：**

```text
填写输入配置
  → 检查环境并扫描
  → 生成草稿和证据包
  → Codex 分析并合并
  → 检查来源、导出材料
```

最终输出为 `project_materials.json` 和 `project_materials.md`，覆盖项目结构、符号对应、目标接口、公共业务约定、测试设施、依赖、已有目标代码、工具链、资源环境、装配约束及支持范围十一类材料。

使用前需准备 Python、JDK，以及进行仓颉结构解析所需的 SDK；具体要求见工具内的 `README.md`。配置示例中的路径必须替换为实际路径。

工具只读分析输入项目，不运行其业务或测试。解析失败、候选关系和待确认信息会保留在输出中；材料结构和来源检查不能证明测试语义等价。

## 4. 验证方法3：仓颉错误业务实现构造

根据仓颉业务代码及对应仓颉测试，使用可复用提示词生成独立的错误业务版本，为后续比较参考测试与翻译后测试的错误检测能力准备材料。

错误主要涉及边界判断、计算与返回值、状态更新、异常和操作顺序。每个版本从同一份原始代码独立修改，只植入一个明确的错误机制，保持接口，不修改测试。

**使用方式：**阅读提示词文件，复制“提示词正文”，填写业务代码、对应测试及可选要求，再核对生成文件和清单。默认首批最多12个版本，不要求凑满数量。

`Experiment/` 保存 Account、InstructionParser、Rectangle 三组既有生成材料。每个批次主要包含：

| 内容 | 用途 |
|---|---|
| `original/` | 原始业务与测试输入 |
| `mutants/Mxxx/` | 各独立错误版本的业务文件、补丁和错误说明 |
| `错误清单.md`、`错误清单.json` | 错误含义、触发条件及预计关联测试 |
| `生成记录.json`、`静态核对.json` | 生成过程和静态核对记录 |
| 同名 ZIP | 批次打包材料 |

后续验证时，让参考测试和翻译后的测试分别运行在同一批正常、错误业务版本上，比较检测结果。每次只使用一个错误版本，完整文件替换与补丁应用二选一。

## 5. 使用关系与验证边界

规则映射回答“**怎样转换**”，项目材料回答“**接入哪些接口和公共代码**”，错误实现材料用于进一步检查“**翻译后是否保留发现错误的能力**”。

三部分可分别使用，当前交付不代表已完成全流程自动翻译与评价。

- 规则中的示例和核验状态以具体条目为准，不能一概视为已运行通过。
- 工具的实现与检查记录见 `docs/IMPLEMENTATION.md`，不据此推断所有解析能力均已验证。
- 错误实现的预计检出结果属于预测，静态核对不等于编译成功或实际检出；运行结论需要独立执行日志支持。
