# Java→仓颉测试翻译运行流程（初稿）

使用者只需提供初始项目材料（通常是 Java 工程根目录）。Agent 自行分析项目、确定测试文件、生成配置并执行下列步骤。仓颉骨架就绪后，本轮同时执行整体翻译和片段翻译。

本轮不进行预处理。骨架翻译读取 `cangjie-skeleton-translator/prompts/骨架翻译提示词.md`，整体翻译读取 `whole-translation/translate_whole.md`，分别遵循各自文件夹中的具体提示词。

**本轮接口约定由第三步统一整理。** 仓颉业务和外部接口说明可选。源码缺失时，第三步从 Java 测试和业务声明拟定 C03。第五步骨架、第六步整体翻译及片段翻译按同一快照、同一条目采用签名和调用方式，保留 pending 状态。遇到未覆盖的调用时回查第三步并补充约定；仍无法决定时记录具体缺口。

本约定是调用各子提示词时的补充要求：子提示词中要求核对真实目标签名、目标定义或公共设施的部分，在本轮改为“存在时核对”；缺少目标接口本身不作为受阻条件。仍需保留原测试行为，不以删除断言、生成业务替代实现或保留空方法来冒充完整翻译。候选译文交付不代表可编译、可运行或语义已验证，未执行的检查继续标为 `NOT_RUN`。

## 文件位置

框架目录：`本分支的主体目录（使用实际绝对路径）`，下文简称 `ROOT`。

真实项目根目录简称 `PROJECT`。本轮输出根目录简称 `OUT`，默认使用 `ROOT/../运行记录/`。已有运行结果时在 `ROOT/../运行记录/` 下选新的独立轮次目录，保留旧结果。使用者显式指定输出目录时使用其指定位置。OUT 必须位于 PROJECT 之外。各阶段产物集中存放在本轮 OUT，按阶段设立子目录。

**查找本次项目的源码、配置、资源、已有目标代码及中间材料时，只查找 PROJECT 和 OUT。** 第一步生成配置后，后续步骤先读 `OUT/translation_config.json`，按其中路径从这两个目录定位；不去其他项目、旧聊天附件或历史实验目录拼凑材料。框架自带的程序、使用说明、通用规则和翻译提示词从下文列明的 ROOT 固定位置调用，不属于项目资料搜索范围。

| 输出子目录 | 保存内容 |
|---|---|
| `OUT/01-project-analysis/` | 项目组成参考文件 |
| `OUT/02-java-skeleton/` | Java 骨架提取结果 |
| `OUT/java-coverage/` | 独立阶段的 Java 源测试覆盖记录、运行配置与原始日志 |
| `OUT/03-project-materials/` | 项目公共材料及工具产生的中间文件 |
| `OUT/04-test-context/<测试类简称>/` | 对应测试类的具体上下文 |
| `OUT/05-cangjie-skeleton/` | 仓颉骨架、成员对应表和相关报告 |
| `OUT/06-whole-translation/` | 按整体翻译提示词生成的最终测试译文、资源和翻译交接记录 |
| `OUT/07-fragment-translation/` | 片段清单、取材记录、材料包、译文、装配后测试和验证记录 |

外层子目录名仅用于分类保存；内部输出沿用各模块文档规定。已有产物时使用新的输出子目录，并让后续步骤读取本次实际路径，不覆盖旧文件。

使用者不必提前列出测试文件、辅助文件或填写配置。这些信息由第一步从 PROJECT 和 OUT 中分析获得；无法确定的目标包名或版本先标为待确定，第五步按源结构和规则拟定本轮采用值并记录依据，不宣称它们是已有工程的真实配置。

## 第一步：分析项目组成

### 输入

| 材料 | 必需／可选 | 从哪里读取 |
|---|---|---|
| 项目根目录 PROJECT | 使用者必需提供 | 使用者指定的真实项目目录 |
| 最终结果输出目录 OUT | 可选覆盖，默认由 Agent 确定 | 默认 `ROOT/../运行记录/`；须在 PROJECT 之外 |
| 项目说明、构建配置 | 模型自行定位，存在时读取 | PROJECT 中的 README、pom.xml、Gradle 配置和模块说明 |
| 测试及相关业务、基类和辅助代码 | 模型自行定位 | PROJECT 的源码目录及测试中的导入、继承和调用 |
| 测试资源 | 模型自行定位，存在引用时读取 | PROJECT 的资源目录 |
| 已有仓颉业务、公共代码、目标接口约定及符号对应 | 可选，模型自行定位 | PROJECT 或 OUT；找不到则记录缺失，继续源端分析 |

### 处理

1. **让模型读取** PROJECT 的目录、项目说明和构建配置，识别模块、源码根、测试框架、版本及资源位置。
2. **让模型查找**项目内实际的 JUnit 测试声明，结合构建配置确定待翻译测试文件，区分真正测试、测试辅助代码和业务代码；将具体文件路径逐项列出，不只登记一个目录。
3. **让模型读取**测试源码及主要相关定义，说明准备条件、被测操作、断言、异常预期和清理行为。默认登记发现的全部有效 JUnit 测试文件；无法支持的测试仍列出并说明问题，不静默缩小范围。大项目按模块分批阅读和后续处理。
4. **让模型排除** `.git`、`node_modules`、`.venv`、`__pycache__`、`target`、`build`、`bin`、`obj`、编译产物、重复历史副本和无关文件，生成实际排除规则；项目所需测试资源不得仅因是二进制文件而排除。不沿符号链接搜索项目外资料。
5. **让模型读取** PROJECT 和 OUT 中已有的仓颉代码与项目约定；存在时核对目标接口和公共设施，未发现时如实记录为可选参考缺失，不转到其他项目补材料，也不因此停止后续翻译。
6. **让模型生成** `OUT/translation_config.json` 和项目组成参考文件，按下表保存。后续各步骤读取配置中的测试清单、路径和排除规则，不要求使用者再次提供相同信息。

### 输出

| 文件 | 保存位置 | 内容与用途 |
|---|---|---|
| `translation_config.json` | `OUT/` 根目录 | 指定项目绝对路径、具体待翻译测试文件、输出绝对路径、排除规则及后续已定位资料 |
| `project_reference.md` | `OUT/01-project-analysis/` | 项目概况、主要目录和模块职责、关键文件、选定测试及依赖、已有目标代码、实际阅读范围和待确认问题；为后续定位材料提供参考 |

`translation_config.json` 是本流程第一步的输出，由后续步骤读取，不直接替代子工具自己的配置。其内容约定如下：

| 字段 | 内容 |
|---|---|
| `project_root` | PROJECT 的绝对路径 |
| `test_files` | 实际待翻译测试文件清单，路径相对 PROJECT，逐文件列出 |
| `output_dir` | OUT 的绝对路径；整体和片段结果分别放在 `06-whole-translation/` 与 `07-fragment-translation/` |
| `test_support_files` | 本轮需要迁移的测试辅助源码清单，逐文件列出项目相对路径；没有时用空数组 |
| `exclude` | 相对 PROJECT 的排除模式及需要说明的排除理由 |
| `source_roots`、`resource_roots` | 自行发现的源码根与资源根，相对 PROJECT |
| `target_sources`、`reference_documents` | 从 PROJECT 或 OUT 定位到的目标代码和相关说明，使用绝对路径；没有则空数组 |
| `target_package`、`versions` | 从项目材料确定的目标包名和版本；尚不明确时填 null 并说明 |
| `unresolved` | 未确认信息、不支持的测试机制和缺失材料 |

配置及参考文件是本流程新增产物，不代替后续工具生成的项目公共材料和具体上下文。

## 第二步：提取 Java 骨架

### 输入

| 材料 | 必需／可选 | 从哪里读取 |
|---|---|---|
| `translation_config.json` | 必需 | `OUT/` 根目录 |
| 选定测试 `.java` 文件或源码目录 | 必需 | 按配置 `test_files` 从 PROJECT 读取；本轮直接使用原文件 |
| 需要一起迁移的测试辅助代码 | 按需 | 根据第一步分析，在原项目中定位 |
| 提取器使用说明 | 必需 | `ROOT/java-skeleton-extractor/README.md`、`docs/骨架提取-使用说明与输出格式.md` |
| 完整 JDK 路径 | 运行必需，可沿用脚本默认值 | 默认 `D:/program_study/yrys/environment-config/tools/jdk-17`，也可指定实际路径 |

### 处理

1. **读取文档**，确认输入编码为 UTF-8、无 BOM，输出目录位于输入目录之外且为新目录或空目录。
2. **调用程序** `ROOT/java-skeleton-extractor/提取骨架.ps1`，传入 `-InputPath <选定文件或目录>` 和 `-OutputDirectory <OUT/02-java-skeleton>`；需要时传入 `-JavaHome <JDK路径>`。
3. **读取产物** `members.json` 和 `extraction-report.md`，核对成员角色、原方法体、字段初始化及提取诊断。
4. **核对产物**是否覆盖选定测试和辅助成员，并将四件套整体交给后续步骤。

目录输入会递归处理其中全部 `.java`，只在全部文件都属于选定范围时使用。多个不连续输入分别调用提取器，分别保存到 `02-java-skeleton/<提取简称>/`；后续读取各自的 `members.json`，不手工拼接成员表。

### 输出

| 文件／目录 | 保存位置 | 内容与用途 |
|---|---|---|
| `original/<原相对路径>.java` | Java 提取输出目录 | 原始源码副本，供读取完整逻辑 |
| `skeleton/<原相对路径>.java` | 同上 | Java 骨架，供模型转换结构 |
| `members.json` | 同上 | 成员 ID、角色、签名、原方法体、初始化及位置 |
| `extraction-report.md` | 同上 | 提取摘要、限制和诊断 |

以上名称和内部结构沿用提取器文档。工具自身的 `build/` 是编译缓存，不属于翻译材料。

## 独立步骤：采集 Java 源测试覆盖记录

在第二步完成后运行。Agent 读取原项目构建配置、`translation_config.json` 和本轮各份 `members.json`，用成员表定位测试类和方法，以原文件中的 JUnit 注解和实际测试引擎核实。测试和业务代码均使用原项目版本编译。

1. 按项目构建配置准备原始业务及测试的编译产物、运行依赖和测试资源。业务 class 目录用于生成报告，测试 class 目录和依赖放入运行类路径。需要构建时使用项目已有构建方式。
2. 按 `ROOT/java-coverage/README.md` 生成工具配置，指定输出 `OUT/java-coverage/` 和完整测试选择器，调用 `python <ROOT/java-coverage/coverage_tool.py> --config <配置文件>`。工具要求输出目录尚不存在，配置先写在 OUT 根目录，运行后随报告归档。第一版逐条运行普通 JUnit 测试，无法适配的用例逐条注明。
3. 核对 `OUT/java-coverage/java_coverage.json` 中的测试标识、测试结果、覆盖状态、方法及日志位置。若构建或运行条件不足，保留已有报告和日志，给出具体未采集原因。无法启动工具时在阶段目录保存带测试清单和原因的未采集报告，供两路读取。

本步骤的输出和第四步样例上下文分别保存。样例上下文按原有方式生成。

## 第三步：生成项目约定与公共材料

工具目录：`ROOT/three-material-get/Project Agreement and Public Materials Generation Tool/src`，下文简称 `PM`。以下程序命令在 PM 目录执行，路径参数使用实际绝对路径。

### 输入

| 材料 | 必需／可选 | 从哪里读取 |
|---|---|---|
| Java 业务、测试及相关辅助代码 | 必需 | 原项目中本次登记的分析范围 |
| `project_config.json` | 必需，先由工具生成再填写 | 保存到 `OUT/03-project-materials/` |
| 已有仓颉业务、公共代码和目标接口约定 | 可选；缺失时目标相关条目可以保持 missing／pending | 按 `OUT/translation_config.json` 从 PROJECT 或 OUT 定位 |
| 项目说明、构建配置 | 存在时纳入 | 第一阶段定位的真实文件 |
| 依赖 JAR、源码根及解析器路径 | 按解析需要提供 | 本地环境和项目配置 |
| 工具文档和提示词 | 必需 | PM 的 README.md、AGENTS.md、prompts/WORKFLOW.md、prompts/ANALYSIS.md |
| 数据格式定义 | 必需 | PM 的 `schemas/` |

本步骤不要求输入第二步的 `members.json`、通用规则或具体上下文。

### 处理

1. **读取文档**，按 README 和 WORKFLOW 确认环境、配置和材料生成要求。
2. **调用程序** `python pmtool.py init --output <project_config.json>`，让模型读取 `OUT/translation_config.json`，将其中路径、源码根和排除规则填写为本工具支持的配置；删除不存在的来源项，避免来源重叠，将 `output_dir` 设为 `OUT/03-project-materials/scan`。两份配置用途不同，不把 translation_config.json 直接传给 pmtool。
3. **调用程序** `python pmtool.py doctor --config <配置>`，检查环境；缺少解析助手时按工具说明准备，解析不可用时保留问题，不把解析失败当成接口不存在。
4. **调用程序** `python pmtool.py scan --config <配置>`，读取生成的 `scan.json`，检查文件范围和解析问题。
5. **调用程序** `python pmtool.py draft --index <scan/index.sqlite> --output <draft.json>`，生成程序草稿。
6. **调用程序** `python pmtool.py packet --index <scan/index.sqlite> --output <packets目录>`，生成证据分片；需要查找具体定义时调用 `query` 和 `show`，查询有后续分页时继续读取。
7. **让模型读取** `prompts/ANALYSIS.md`、贡献格式 schema、程序草稿和证据包 `manifest.json` 列出的全部相关分片，按模块分析九类项目材料；根据草稿中的 target_contract_review 选择目标源码核查或从源测试拟定接口，保存 `contributions/analysis_*.json`。若只读了部分范围，保留部分完成状态。
8. **调用程序** `python pmtool.py merge --index <索引> --base <draft.json> --analysis <实际贡献文件列表> --output <reviewed.json>`；只有满足工具完整覆盖要求时才加 `--mark-complete`。
9. **调用程序** `python pmtool.py check --index <索引> --materials <reviewed.json> --live`，检查结构和来源，处理实际报错。
10. **调用程序** `python pmtool.py export --index <索引> --materials <reviewed.json> --output <final目录>`，导出后续使用的 JSON 和 Markdown。

默认排除目标参考测试。未完整分类的目标代码按工具规则隔离，不绕过配置向模型提供。材料中的候选、推断、缺失与冲突保留原状态。

材料 2.0 统一读取 C03「目标接口约定」的对应、签名、调用形式及行为；材料 1.0 仍分别读取 C02、C03、C04。按条目 ID 引用同一快照，区分实现证据与 pending 拟议约定。骨架、整体译文与各片段采用同一签名；冲突写入交接记录，未覆盖的调用回查源测试并补充约定。

### 输出

以下路径都位于 `OUT/03-project-materials/`。

| 文件／目录 | 内容与用途 | 名称依据 |
|---|---|---|
| `project_config.json` | 本工具的输入配置 | 文档示例名，本流程沿用 |
| `scan/scan.json` | 本次范围、版本、数量和解析状态 | 工具固定文件名 |
| `scan/index.sqlite` | 源码快照、成员、引用、事实和问题索引 | 工具固定文件名 |
| `scan/parser_artifacts/` | 解析副本及相关解析输出 | 工具原有目录 |
| `draft.json` | 程序草稿 | 文档示例名，本流程沿用 |
| `packets/manifest.json`、`packet_*.json` | 证据包清单和实际分片 | 工具命名；外层目录由本流程选定 |
| `contributions/analysis_*.json` | 模型按 schema 生成的分析贡献 | 文件及目录名由本流程选定 |
| `reviewed.json` | 合并后的项目材料，可能仍是部分分析 | 文档示例名，本流程沿用 |
| `final/project_materials.json` | 后续翻译读取的结构化公共材料 | 工具固定文件名 |
| `final/project_materials.md` | 同一份公共材料的可读说明 | 工具固定文件名 |

`doctor` 和 `check` 的结果直接读取，不额外规定新的结果文件。草稿、索引和贡献保留供查证；后续翻译主要读取 final 下的两份公共材料。

## 第四步：获取当前测试上下文

工具目录：`ROOT/three-material-get/context-lookup`，下文简称 `CTX`。

### 输入

| 材料 | 必需／可选 | 从哪里读取 |
|---|---|---|
| 完整 Java 项目根目录 | 必需 | 读取 `OUT/translation_config.json` 的 project_root；不能只用提取结果的 original/ 代替 |
| 选定测试文件或完整方法标识 | 必需 | 读取配置 test_files，再从 PROJECT 定位 |
| 使用说明与输出格式 | 必需 | CTX 的 README.md、AGENTS.md、docs/使用说明.md、docs/输出格式.md |
| 非标准源码根、资源根 | 按需 | 第一阶段定位的项目内目录 |
| Java／javac 路径和查找上限 | 按需 | 本地使用与验证说明及实际环境 |

本步骤不要求 `selection.json`，也不要求 Java 成员表、规则库或项目公共材料。

### 处理

1. **读取文档**及 `OUT/translation_config.json`，确认测试标识、源码范围和工具限制。依据配置排除生成目录和历史副本；工具没有通用 --exclude 参数，不虚构该参数，使用其支持的 --source-root 限定真实源码范围。
2. **调用程序**，在 CTX 目录执行 `python context_tool.py --project <项目根> --target <测试文件相对路径或完整方法标识> --output <OUT/04-test-context/测试类简称>`；按需增加 `--source-root`、`--resource-root`、`--java`、`--javac` 等参数。
3. **调用程序**，为其他选定测试类分别执行同一命令并使用独立输出目录。当前优先按完整测试类获取上下文。
4. **读取产物**，核对完整测试类、相关代码、初始化与清理、辅助方法、资源内容和实际来源。
5. **读取产物**中的 `unresolved`、`project_issues` 和 `completeness`，识别材料缺口；必要时让模型补读真实源码，明确区分工具查找结果与模型补充分析。

输出目录必须在输入项目之外且尚不存在，不提前创建测试类输出子目录。若指定的项目根包含 OUT，应先改用独立的真实项目根。

### 输出

## 第六步：执行整体翻译和片段翻译
