# 两个骨架工具的优化方案

本页供组员评审和选择后续改动。每项列出当前实现的限制、改动带来的收益和验收方式。以下为待实施的方案，已完成的检查见[骨架样例运行记录](../运行记录/骨架样例/README.md)。

## 一、Java 骨架提取器

提取器用 JDK 语法树读取源码，把声明保留在骨架中，把原方法体、成员角色和源码位置写入 `members.json`。[提取器源码](02-Java骨架提取器/tools/JavaTestSkeletonExtractor.java)

| 方案 | 改法和理由 | 怎么验收 |
| --- | --- | --- |
| 识别 JUnit 4 测试和生命周期 | 在 `resolve()` 和 `visitMethod()` 中支持 `org.junit.Test`、`@Before`、`@After` 等，并保留 `expected`、`timeout` 的原始声明。已有 Aho-Corasick 样例的 JUnit 4 测试被标为 `helper`，修正后翻译阶段才能按测试处理。 | 复跑 Aho-Corasick，对照原测试核对角色与注解参数。用同名自定义注解检查误判，确认原方法体保持一致。 |
| 识别 JUnit 3 测试 | 判断类是否继承 `junit.framework.TestCase`，再按方法签名识别 `test*`、`setUp`、`tearDown`。Diff Utils 的测试采用这种写法，单靠注解会漏掉。 | 用 Diff Utils 的 `DiffTest.java` 核对测试名单，并确认普通类中同名的方法仍识别为辅助方法。 |
| 允许选择目录中的提取范围 | 在文件和整目录输入之外，增加文件清单或包含、排除选项。这样可以把目标测试和所需辅助类一起送入提取器，减少无关源码进入成员表。 | 在 jsoup 源码目录只选择 `SelectorTest` 及所需辅助源码，核对输出文件清单、顺序和原有成员 ID。 |
| 补充继承和初始化信息 | 在类元数据记录 `extends` 和 `implements`，为类级初始化块记录位置和静态属性，基类来源缺失时给出提示。当前初始化块保留在骨架中，翻译阶段仍需逐文件追踪准备和清理逻辑。 | 用一个带基类和静态初始化块的测试样例核对来源、初始化位置和缺失基类提示。 |
| 记录参数化测试的数据来源 | 在现有参数化角色识别上补充数据源类型和引用，例如 `@ValueSource` 的值、`@MethodSource` 的提供方法。后续生成仓颉测试时据此判断用例如何展开。 | 用固定值及方法供数两类样例核对数据引用，缺失提供方法时给出待确认项。 |

可先处理 **JUnit 4 识别**。已有项目暴露了误分类，修改范围集中，也能直接拿原测试和现有成员表做对照。JUnit 3 和参数化数据源可根据下一组评测选题推进。

## 二、仓颉骨架翻译器

模型按提示词生成仓颉声明，Python 脚本复核已有样例。生成规则和检查实现分别见[骨架翻译提示词](03-仓颉骨架翻译器/骨架翻译提示词.md)和[检查脚本](03-仓颉骨架翻译器/check_skeleton.py)。

| 方案 | 改法和理由 | 怎么验收 |
| --- | --- | --- |
| 用修订版提示词重新做一次生成验收 | 固定 Java 骨架、成员表和项目约定。生成前列出缺失或冲突的规则、类型和配置，生成后保存骨架、成员映射和翻译报告。现有样例来自前一版提示词，需要为修订版建立直接证据。 | 用 Smart Library 和 Commons IO 重生成，核对 17 个源成员都有处理记录，并确认缺失的真实接口会记录为阻塞。 |
| 让检查脚本接收项目参数 | 接收成员表、仓颉文件、目标包或类及输出位置。当前项目和包名在 `CASES` 里固定，每加一组样例都需要改脚本。 | 用同一版本脚本检查现有两组，再检查一组新文件。输入有误时指出具体文件、包或类。 |
| 校验新版成员映射和报告 | 按源成员 ID 核对覆盖、重复和目标定位，检查 `mapped`、`reused`、`blocked` 及待填位置。对参数化展开的一对多映射单独校验，避免按方法名误判。 | 分别检查漏成员、目标签名不符、合法一对多和有明确原因的阻塞，确认诊断指向具体源成员。 |
| 扩展声明检查 | 将当前普通无参测试和 BOM 字段的固定匹配，扩展到辅助方法、生命周期、普通字段、多个类和重载。定位时使用所属类和签名，减少因改名或格式变化导致的误判。 | 对同一骨架调整空白和换行应仍通过。删除辅助方法或改错签名时应报出对应成员。 |
| 分别记录结构、编译和行为验证 | 单独保存结构检查、仓颉编译、测试发现和实际执行结果。标明是否使用临时类型。测试方法体填充后，再使用对应的真实仓颉业务和原测试基线核对结果。 | 用已有骨架验证能正确记录测试发现。用一组填充完成的双语测试验证能保存真实执行结果，并识别有意改错的断言。 |

可先**重新生成两份样例，并移除检查脚本对固定样例路径的依赖**。一个方案回答修订提示词实际生成了什么，另一个方案降低检查新项目的成本。
