# 重要源码阅读指南

本文帮助组员从真实函数理解工具功能。先看 [调用流程](职责分工与流程.md)，再按下面的六段主线读源码；任务组织与所需材料见 [使用说明](README.md)。这里介绍的是普通本地函数，没有隐藏 Agent 或服务器。

```text
context_tool.main
  → indexer.build
      → project_source.scan_project：识别、原字节冻结和来源清单
      → backend.analyze：运行本项目 SymbolFacts.java
          → JavaParser.parse / findAll：结构和内部语句
          → MethodCallExpr.resolve 等：静态目标证据
      → facts.normalize_facts：路径、UTF-16 区间、成员身份
      → internal_analysis.build_internal_analysis：语句/检查/特征关联
      → 保存 project_schema 与索引摘要
  → Project：加载同轮索引和冻结源码
      → assemble.write_suite：shared、tests、tasks 和整类视图
      → read / related / resolve / query_member / query_features：按需补查
```

## 1. 接收项目：scan_project

project_source.py 的 scan_project() 协调 layout.inventory_paths()/discover()/file_role()，先枚举文件和识别根，再按原字节复制到 source/。复制前后核对 SHA-256 和文件集合，发现过程中变动就失败；以后原项目被编辑不会使旧索引偷偷读取新文件。

layout.discover() 只读取常规目录和字面 Maven 声明，不执行构建。资源目录里的 .java 保留为数据；普通未归类 Java 作为辅助源码并记录问题。safe_path() 拒绝相对路径越界与链接，ProjectSource 每次接收快照再核对清单。

输入是完整项目和范围选项，输出是 source_manifest 与可分析的 ProjectSource。它承担原来准备阶段的接收/冻结职责，不生成其他模块的骨架配置。

## 2. 解析代码：analyze 与 SymbolFacts

backend.analyze() 校验离线 JAR，写入实际解析任务，调用 javac 编译本项目 SymbolFacts.java，再用 java 运行其 main()。被分析项目只作为数据读取；本地项目 JAR 只传给类型求解器，不放进本工具运行时类路径。

JavaParser.parse() 得到 CompilationUnit；syntaxFacts() 遍历类型、CallableDeclaration、VariableDeclarator、InitializerDeclaration 等，记录声明、参数、注解及初始化。结构提取不要求外部依赖绑定成功。

MethodCallExpr.resolve()、ObjectCreationExpr.resolve()、FieldAccessExpr.resolve()、NameExpr.resolve() 分别尝试定位方法、构造器和字段。CombinedTypeSolver 组合 JDK、源码根和本地 JAR 证据。静态声明不等于多态运行时实现，异常会保存为原因而不是按名字猜。

field() 处理 int a=1,b=2 等情况：toAst() 若返回整条 FieldDeclaration，就继续按变量名找到 VariableDeclarator。命名/匿名类型有自己的归属，随后以声明位置核对，避免把匿名类 first 字段错配到外层同名字段。

bodyNodes() 收集 Statement、LambdaExpr、CatchClause、SwitchEntry 等。analysisOwner() 确定真正成员，跨匿名/局部类型边界时停止；analysisRole() 分开 THEN/ELSE、TRY/CATCH/FINALLY 和 LOOP_BODY。这里提取语法包围，不计算分支可达性、循环次数或执行轨迹。

## 3. 建身份与引用：normalize_facts 和 build

facts.normalize_facts() 将解析路径转为包内相对路径，分配快照+文件+种类+区间的机器 key；显示名仅方便人读。引用按最小包含成员区间归属，因此内层方法引用不会都落到外层测试方法。

Java String 下标按 UTF-16 码元计数。Python 先 encode('utf-16-le') 再按两字节切片，避免 emoji、制表符和 CRLF 造成位置错读；结束位置不包含。normalize_facts 是数据整理函数，不会转换 Java 源程序。

indexer.build() 先登记全部声明的位置和完整签名，再给引用建边。同名候选保留列表，声明未唯一对应时保留 ambiguous/unresolved；有可靠字段位置时不回退到外层同名字段。annotation_name() 结合实际 import 识别 JUnit，项目 fake.Test 不当框架测试。

schema 的 files/types/members/references 是项目事实，internal_analysis 是内部分析。源码正文统一从 source/ 取，不在每张表里重复保存。

## 4. 内部分析：build_internal_analysis

internal_analysis.build_internal_analysis() 把语句节点、成员 key 和引用位置关联。parent_key 表示语法父节点，source_order_in_parent 表示源码顺序；引用附 analysis_node_key/control_node_keys，方便查询原表达式所在区域。

assertion_basis() 分开静态框架绑定、明确 import 支持、Java assert 语法和同名候选。已知名字不等于框架断言：项目方法 assertEquals 保留 CANDIDATE，自定义 assertSomething 需 Agent 阅读。lambda 内检查保留 deferred_context；Java assert 另保留启用条件。

features 只记录重载组、构造委托、初始化、匿名类型、lambda 等待复核对象。所有项都是 REVIEW_REQUIRED，source_transformation 为 UNSUPPORTED，代码没有改名或改造源调用点。

query_member() 为 analyze 命令提供并行分页，三个列表分别取同一个 offset/limit；可选原文共用字符预算，超限仍保留 key/位置。context_summary() 只把少量步骤入口及计数放入初始视图，其余按需查询。

## 5. 选取上下文：assemble

assemble() 从共享初始化/生命周期或所选测试开始，用 deque 队列广度优先展开已绑定依赖，用 visited 防止递归循环。测试辅助方法保留正文；业务方法/构造器默认止于签名，需要理解时再 read。

assemble_class() 组织共享材料；assemble_test() 组织单条测试差异。provided_by() 只复用共享文件中实际纳入的源码区间，共享签名不能冒充完整正文，预算缺失也不能当已提供。

write_suite() 为一个完整测试类输出 shared、逐条文件、tasks 和整类阅读入口；共享引用带摘要和 index_id。compact_context() 压缩重复元数据，保留已纳入源码、未解析和省略项，不用自然语言摘要替代辅助断言。

语句内部分析不改变这些展开规则，也不新增可执行测试方法。整体翻译仍以完整测试类为输出单位。

## 6. 查询原文：Project

Project.__init__() 验证 schema、manifest、快照、外部 JAR 和附加材料，再建立 by_type/by_caller/incoming 内存表。每个 CLI 查询是一次本地进程，不需要常驻服务。

read() 通过 span() 校验文件摘要并切出真实声明；字段的绑定区间可指具体变量，阅读时使用 read_start/read_end 返回完整字段声明。related() 分页取出/入边；resolve() 返回构建时已有绑定，不重新调用 Java 解析。

test_target()/hierarchy() 确定所选 JUnit 测试、有效覆盖与生命周期，保留歧义和未知顺序；resources() 只根据已确认 API、可确认路径和包锚点找资源，动态工作目录不猜。

## week12 接口函数

`java_members.import_members()` 先从表的 input_root/source_file 找回项目相对路径，与本轮快照 SHA-256 比对；再按所属类型、种类、名称和 UTF-16 声明区间唯一对应。字段允许“整条声明”与“具体变量”区间不同，但同时核对类型和阅读区间。方法额外对照原方法体。只有同版可对应数据才进入 `member_links`。

该函数的 `parent_of()/lineage()` 在明确 import、同包和已知 TestCase 范围内记录源侧继承链。成员证据、JUnit 3 角色和 test_invocations 分开存；普通引用的 SymbolSolver 绑定不因此改变。`Project.test_target()` 保留执行类型，选择真正声明的测试 key；`assemble()/write_suite()` 将两种身份带到初始上下文。源码推断与真实 JUnit 发现始终分开。

`prepare_skeleton_check.prepare()` 解析整体任务和骨架组，核对原提取文件的来源摘要，在新目录复制 Java 提取和目标骨架；只重定向副本中的成员表/目标路径，生成检查器专用配置和适配清单。它不翻译、不改源 ID、不将 blocked 变成 mapped。输出冲突、路径重叠和材料不一致会明确失败。

`check_skeleton.verify()` 属于蔡俊杰上游实现：加载成员与目标映射、定位目标声明、核对签名和填充槽，再检查遗漏、重复与包名。它在整体填充前运行；逻辑正文填好后继续使用原占位检查规则会误报。完整输入输出见 [对接说明](集成适配/README.md)。
