# 仓颉骨架翻译工具的文件讲解

这一部分由模型生成规则、结构检查代码和对应样例组成。生成阶段的规则集中在提示词中。它规定如何从 Java 声明得到目标声明，遇到类型、注解或接口缺项时如何记录，以及产物应该包含什么字段。[翻译提示词](骨架翻译提示词.md)

| 文件或目录 | 作用 |
| --- | --- |
| `骨架翻译提示词.md` | 依次规定输入、处理和输出。处理部分包含声明梳理、规则选取、目标包与签名确定、占位和成员对应。 |
| `check_skeleton.py` | 核对已生成的样例并写出样例成员映射。 |
| [`model-output/`](../../运行记录/骨架样例/model-output) | Smart Library 和 Commons IO 的两份仓颉测试骨架。 |
| [`member_mapping.json`](../../运行记录/骨架样例/member_mapping.json) | 保存 Java 成员和仓颉声明的对应关系。 |
| [`compile-support/`](../../运行记录/骨架样例/compile-support) | 保存既有样例编译使用的临时 BOM 类型声明。 |
| [`生成记录.md`](../../运行记录/骨架样例/生成记录.md) | 说明当前产物所用的提示词版本和验证范围。 |

检查脚本可以分三段阅读。[查看检查代码](check_skeleton.py)

1. `CASES` 写明支持检查的项目、仓颉包名和类名。`require()` 在条件不满足时给出错误。
2. `main()` 读取两个 Java 样例的 `members.json`，核对原文及 Java 骨架的 SHA-256，再检查仓颉包、测试类、方法、字段和占位。现行规则针对普通无参测试与 Commons IO 的 BOM 字段。
3. 每检查到一项有效声明，就记录源成员 ID、目标文件和行号，以及 `fill_slot`。`body` 对应方法体，`initializer` 对应字段初始化。最后将列表写入 `member_mapping.json`。

例如，`canBorrow_returnsFalse_whenMemberIsNull()` 对应仓颉类中的同名 `@TestCase`，映射标记 `fill_slot: body`。Commons IO 的 `TEST_BOM_1` 当前用 `Option<ByteOrderMark> = None` 占位，映射标记 `fill_slot: initializer`。[仓颉骨架样例](../../运行记录/骨架样例/model-output/DefaultBorrowPolicyUnitTest.cj) · [成员对应表](../../运行记录/骨架样例/member_mapping.json)

一个可单独优化的点是检查脚本的样例配置。当前的项目、包名和类名写在 `CASES` 中。可以把成员表、仓颉文件和目标范围改为参数，并用正确骨架和漏掉一个测试的骨架各验证一次，确认错误报告能定位对应 Java 成员。
