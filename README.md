# Java → 仓颉测试翻译静态验证工具

给定 Java 原测试和一份最终仓颉译文，工具帮助 Agent 逐个回答：两个测试准备了什么、操作谁、按什么顺序检查了什么？每项结论都可以追到源码片段。缺少仓颉业务或目标接口约定时，仍可检查源码上写明的内容。

**先看一次真实结果**：[积分钱包整体译文的验证报告](runs/points-wallet-whole/deliverables/report.md)。本轮核对了两个测试的六条断言，保留了两个测试各自的接口未知项。

```text
Static Validation/
├─ README.md、版本更新记录.md
├─ src/                 命令行程序、总控及五步提示词、使用说明、回归测试
├─ samples/             本轮翻译输入的索引，指向现有 Translation-all 产物
└─ runs/             按轮保存过程与交付物
   └─ points-wallet-whole/
      ├─ process/       五个阶段各自的依据和处理结果
      └─ deliverables/       可读报告、结构化报告、两份带注释的测试源码
```

### 一轮验证怎样进行

1. **按骨架找对应测试。** 程序从 Java 成员表列出应检查的测试，根据成员映射到所选路线的最终译文定位。源清单独立保存，后面可以发现漏做。
2. **两侧分别标注。** 两个新会话各读本侧材料，在源码副本中按统一环节标注。程序核对原文引文和行号，插入注释后还原检查原始行。
3. **逐个比较。** 模型按测试、环节、具体代码比较并回查差异。程序校验材料版本、片段引用及接口依据。
4. **清点与补查。** 按最初源清单检查每条测试的去向。有涉及多条测试的矛盾时，回查准备或清理方法，并更新受影响的判断。
5. **生成两种报告。** 程序汇总结构化记录，模型写可读说明。两份报告与标注源码复制到同一交付目录。

### 如何读结论

每个测试保留多条判断。一条断言是否仍要求“余额等于 70”，可以对照两侧源码；两个业务接口是否都以积分为单位，需要接口依据。任一已确认差异使单元总体为“发现差异”；其余项中有重要未知时为“信息不足”；全部已有依据时才记“在所列前提和范围内一致”。即使综合结论为信息不足，已核实的断言和顺序仍可单独查看。

### 英文目录与旧记录的对应关系

旧文档中的“样例材料”“运行记录”“过程文件”“交付文件”依次对应 `samples/`、`runs/`、`process/`、`deliverables/`。在每轮的 `process/` 下，按编号依次查看 `01-alignment/`（定位测试）、`02-annotations/`（两侧独立标注，分别在 `Java/` 和 `Cangjie/`）、`03-comparison/`（比较及回查）、`04-audit/`（清点范围）和 `05-report/`（汇总与交付核对）。新运行也使用这套名称。单独下载本分支后，可以直接阅读钱包样例和历史报告；重新生成结果还需准备对应的 Translation-all 输入。
