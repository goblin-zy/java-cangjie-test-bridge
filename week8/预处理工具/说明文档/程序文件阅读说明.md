# 程序文件阅读说明

本文用于阅读交付代码。先了解入口和调用关系，再按文件说明定位具体功能。使用操作见使用说明，输出字段见输出文件与字段使用说明。

## 1. 先看这条调用链

窗口通过主程序执行分析：

```text
窗口入口
启动预处理.cmd
 → launch.ps1
 → 主体/scripts/start_gui.ps1：找到Python并打开窗口
 → 主体/src/gui.py：收集选择、显示状态
 → desktop_workflow.py：检查环境和目录
 → preprocess.prepare：开始正式分析

共同分析过程
preprocess.prepare
 → 保存测试及资源副本
 → 编译并运行tools/JavaFacts.java：取得语法结构
 → 保存成员原文与引用
 → 调用analysis_reports.py：整理特性、能力和交接清单
 → 写入本轮输出目录

接收结果时
check_handoff.py：读取输出目录，核对交接材料
```

Java分析器使用JDK编译和运行，处理对象是复制后的Java源文件。测试用例的实际执行由后续验证环节安排。

## 2. src目录里各文件负责什么

### 2.1 preprocess.py：把整次预处理串起来

这是主程序，窗口调用其中的prepare。

接收工程根、结果位置、测试根、资源根以及java/javac命令。它先检查目录，再复制文件，调用Java分析器，取回结构信息，组装成员原文，生成结果文件。

重点按以下顺序阅读：

1. main：程序的直接执行入口；窗口分析使用prepare函数。
2. prepare：从检查输入到写出结果的完整过程。
3. walk：遍历明确选择的目录，同时检查链接。
4. save与sha：分别负责保存JSON和计算文件摘要。

prepare中的关键动作包括：

- inventory收集文件路径、类别、大小和摘要，形成snapshot_id。
- javac先编译工具自带的JavaFacts，java再运行该分析器，结果通过JSON传回Python。
- 根据Java给出的UTF-16区间取得原成员全文，写入members。
- 调用analysis_reports中的函数组织报告。
- 根据解析和编码情况决定状态，异常信息写入FAILED.json。
- 复制共用提示词、模块提示词和下游说明，最后生成manifest。

修改输入范围、复制策略、结果生成顺序或输出状态时，从这里开始阅读。单独调整特性识别时，主要阅读analysis_reports。

### 2.2 tools/JavaFacts.java：读懂Java文件的结构和位置

它相当于语法读取器。接收一个文件列表，逐个解析冻结副本，输出JSON。

main创建JDK解析任务，task.parse取得语法树。TreePathScanner遍历树上的类型、方法、变量、初始化块及调用。SourcePositions提供每个结构在原文件中的位置。

主要记录包括：

- 类型：名称、所属位置、继承与接口写法、注解。
- 成员：字段、方法、构造器和初始化块；方法记录参数类型和返回类型写法。
- 调用：调用者、接收表达式、名称、参数及出现位置。
- 解析问题：文件、行号及诊断信息。

visitClass、visitMethod、visitVariable、visitBlock分别对应以上声明；visitMethodInvocation、visitNewClass、visitMemberReference记录普通调用、创建对象和方法引用。

例如values.clear()会得到接收表达式values和名称clear。被调定义及框架归属需要下游进一步确认。构造器在方法类记录中使用<init>名称。

需要增加一种源代码语法事实时，先在这里取得准确节点和位置，再由Python组织输出。

### 2.3 analysis_reports.py：把语法事实整理成下游可用的报告

它接收已经取得的成员、文件清单和语法事实，负责报告分类与组织。

| 函数 | 作用 | 对应结果 |
| --- | --- | --- |
| `member_key` | 给本快照中的成员生成唯一引用键 | members中的source_member_key |
| `feature_report` | 标出支持的语法情况 | translation_features.json |
| `capability_report` | 说明处理范围和能力层级 | capabilities.json |
| `source_mapping` | 对照源文件与副本 | source_mapping.json |
| `downstream_report` | 列出各模块拿什么、补什么、交什么 | downstream_handoff.json |

feature_report支持字段初始化、初始化块、声明重载候选、多构造器、显式this/super调用及列出的注解名称。它通过同类型声明分组、注解短名匹配等规则生成提示，并保留语法依据。

成员键的计算将snapshot_id、文件路径、id和起止区间组合后计算SHA-256，得到source_member_key；snapshot_id则由文件清单摘要产生。它们用于源快照内的稳定对应。

CONSUMERS保存六类模块的配置，包括模块名称、prompt文件、可用材料、补充条件和预期输出。程序据此生成下游清单；提示词正文保存在主体/prompts。

增加特性提示时，修改feature_report并明确识别范围；调整下游交接时，核对CONSUMERS和对应prompt是否一致。

### 2.4 gui.py：负责用户看到的窗口

它创建目录选择框、按钮、活动条和日志区域。窗口将用户选择整理为参数，交给共同的prepare执行。

主要阅读位置：

- App.__init__：窗口布局及控件。
- use_sample、fill_project：样例和工程目录如何填入。
- load、save：载入与保存本机设置。
- environment：请求JDK环境检查。
- start：收集输入、检查选择、在后台启动分析。
- poll：从队列接收后台消息，刷新状态和结果按钮。
- open_result、open_report：打开本轮结果或结果概览。

耗时分析放在后台线程，窗口线程通过消息队列读取结果。调整按钮、提示文字或布局时从这里入手；核心分析行为由preprocess负责。

### 2.5 desktop_workflow.py：替窗口处理环境和路径问题

这个文件把与界面外观无关的辅助操作集中起来，供gui调用。

| 函数 | 作用 |
| --- | --- |
| `check_environment` | 检查java、javac能否启动及其版本要求 |
| `relative_root` | 将所选子目录转换为工程相对路径 |
| `validate_inputs` | 检查工程、结果父目录和输入根之间的关系 |
| `new_output` | 根据时间生成一个新结果目录名 |
| `load_settings` | 读取设置并解释路径基准 |

用户点击开始前，这些函数检查目录是否存在、输入根是否重叠、结果位置是否适合。prepare还会检查核心输入，核心分析采用相同输入约束。

修改环境提示、窗口设置读取和轮次命名时阅读这里；底层输入整理位于preprocess。

### 2.6 check_handoff.py：在结果交出去时做材料检查

它接收--run指定的结果目录，读取handoff和manifest，检查目录中的材料是否符合交接约定。

check负责检查文件集合、摘要、快照身份、源文件对应、成员原文区间、成员键、特性引用及下游文件路径。main负责直接调用入口和错误提示。

它输出HANDOFF_MATERIAL_CHECKS_PASSED或具体错误。该结果描述交接材料的一致性；构建、测试执行和目标行为各有后续检查环节。

例如成员原文被改动、提示词文件丢失、快照混用，接收者可通过这个程序定位问题。

## 3. src之外的文件怎样配合

启动预处理.cmd是Windows窗口入口；launch.ps1将调用转给主体/scripts/start_gui.ps1。后者选择满足要求的Python；窗口入口检查Tkinter并启动gui.py。-CheckOnly用于检查启动条件。

config/example.json保存输入工程、结果目录、测试与资源根、JDK命令。配置中的工程和结果父目录相对配置文件所在目录解释，源码根相对工程解释。

prompts/handoff.md是共用交接要求，其余六份prompt分别服务上下文、Java骨架、仓颉骨架、整体翻译、片段翻译和验证。下游执行者按清单选择职责并调用对应工具或Agent。

说明文档负责操作、接口和接收约定。样例/结果保存一次实际分析输出，样例源码保存在其中的input，运行记录.txt说明实际进行了哪些检查。

## 4. 用样例对照程序输出

打开样例/结果/input/src/test/java/sample/ListTest.java，再依次查看：

1. members.json：找到addThenClear，核对原方法全文及source_member_key。
2. test_structure.json：查看该类的字段、方法、注解和调用位置。
3. test_candidates.json：查看按Test名称识别的方法候选。
4. translation_features.json：查看字段初始化、BeforeEach/AfterEach名称提示和expectSize重载候选。
5. external_references.json：查看JUnit导入及values.clear等调用文本。
6. source_mapping.json：核对源路径与input副本的对应。
7. downstream_handoff.json：选择一个模块，查看available、missing、expected及prompt。

接着执行check_handoff检查该结果，再在窗口中载入设置并复跑一次。这样可以把源码中的每个动作与实际文件对应起来。

## 5. 下游怎样拿这些结果继续做

所有模块先读handoff、capabilities和issues，再按downstream_handoff取材。

| 下游部分 | 重点取得 | 接着完成 |
| --- | --- | --- |
| 上下文查找 | 引用表达式、源成员及位置 | 查询定义、接口和契约，返回来源及待确认项 |
| Java骨架提取 | 完整源码、成员原文及来源对应 | 提取骨架并建立成员对应 |
| 仓颉骨架生成 | 源结构、特性及目标接口 | 生成目标声明、占位和位置映射 |
| 整体翻译 | 完整测试、资源和接口材料 | 生成完整测试译文 |
| 片段翻译 | 成员原文、单元清单及目标位置 | 翻译、回填并记录状态 |
| 验证 | 源身份、译文及完整运行环境 | 分别检查构建、执行和错误发现能力 |

其中目标接口、单元清单、目标位置及完整运行环境按对应下游要求提供。预处理以文件方式交出材料，流程执行者负责组织后续运行。
