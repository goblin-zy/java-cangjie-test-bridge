# Java测试整体翻译任务

你负责在**已有仓颉测试骨架中填充一个完整Java测试类及必要测试辅助逻辑**。直接读取本地输入、生成文件并记录结果，不要求使用者复制源码或逐方法下发任务。

“整体”指配置明确选中的一个完整测试类，不代表翻译整个代码仓库。一次任务中有多个类时，分别核对和记录，每个类按完整单位处理。不要转为片段选取、逐单元回填流程，也不要翻译被测业务算法。

## 一、任务入口与输入约定

本次配置文件路径：**由调用者提供实际路径**。先读取该文件，再执行本提示词。

配置可以沿用已有`translation_config.json`；下述字段是本任务交接约定，不代表仓库已实现配置解析器。名称不同但含义明确的已有配置可由你只读归一化到记录中，不要求使用者重新填写相同材料。关键路径、翻译对象和允许修改范围不明确时，先报告缺项，不擅自扩大范围。

必须具备以下输入：

|输入|需要读取的实际内容|
|---|---|
|本次范围|项目路径、选中的完整测试类/文件、输出目录、排除范围及修改约束|
|完整Java原文|同版本预处理结果，或未改写时的原源码；包括注解、导入、字段初值、方法体及必要辅助代码|
|`members.json`|源成员ID、角色、签名、原始方法体/初始化式、源码位置及提取状态|
|仓颉测试骨架|本次允许填充的真实`.cj`文件，不是历史完整参考译文|
|成员对应|已有`member_mapping.json`或`member-map.json`及其路径基准|
|通用规则|实际提供的`translation_rules.json`及适用版本说明|
|项目公共材料|`project_materials.json/.md`或等价已确认材料，包含目标接口、包名、公共约定和可复用设施|
|目标业务与资源|允许读取的真实仓颉接口/实现、必要资源和配置，以及哪些只是声明占位|
|当前样例上下文|已有`context_<标识>.json/.md`；缺少且确有查找需要时可调用上下文工具补充|

路径以当前 GitHub 工作区的仓库根为基准。先在根目录运行 `python week8/whole-translation/fetch_inputs.py`，按 `github_inputs.json` 从固定 GitHub 提交取出依赖到 `.deps/`。配置、输出记录和文件引用统一使用工作区相对路径。映射条目中的路径按 `member_mapping.base_dir` 解析，成员表里的原文路径按成员表所在提取目录解析。历史元数据中的绝对路径仅作来源说明。

`targets[].target_output`与`constraints.allowed_output_files`相对于本次`output_dir/translated/`，不得包含绝对路径或父目录跳转。允许新增测试辅助代码时，可在`translated/helpers/`保存确有必要的文件，并在结果中逐一说明；未获允许时报告缺失。资源按约定写入`output_dir/resources/`，元数据写在输出根，不改写配置指定的任何输入。

如果预处理改写过源码，原文、成员表、骨架、上下文必须对应同一处理版本；原/新代码对照和未处理事项一并读取。不能使用新方法体配旧偏移或旧映射。

## 二、读取和检查输入

1. 检查路径是否存在、输出目录是否为新目录、允许输出的目标文件是否明确。只向本次输出目录写入，输入源码、成员表、规则、映射、骨架和业务实现保持原样。
2. 完整读取选中测试类和必要辅助定义。读取成员表及本类相关映射，按源成员ID建立对应；同名方法不能代替完整ID，重载不能只凭方法名区分。
3. 核对源文件摘要、方法体/初始化式与成员表，按真实位置确认骨架目标声明。`target_line`是定位提示，填充后行号可能变化，不能作为唯一依据。
4. 读取相关规则、项目约定及目标业务声明。区分已确认接口、候选对应、未解决项和仅供编译的占位声明；来源冲突时保留问题，不自动挑一个有利于生成的版本。
5. 检查每个待填成员是否有目标位置。允许一个源成员对应多个目标成员，但每条对应必须有依据；完全相同的目标槽不能重复填入。直接复用成员需指向真实目标定义。
6. 提取本类的测试、准备/清理、构造、字段、辅助方法和初始化需求；逐项记录哪些属于本次范围，哪些已由公共设施承接。不得只处理带测试注解的方法。

输入检查结果写入`input_manifest.json`。其至少记录：实际输入路径、文件SHA-256、版本/处理来源、选中类及成员表、允许/禁止读取范围、已有上下文路径和关键缺项。它是本任务生成的记录，不是要求使用者先制作的清单。

如果上游说明要求现场生成某份成员表，而配置中的源代码和固定版本依据已齐备，可以调用已有Java提取器，在本次独立准备目录补齐源侧提取结果；记录原逻辑路径与实际生成路径的对应，逐ID核对既有成员映射。不能覆盖上游目录、重新猜造仓颉骨架或用重提取结果掩盖版本差异。缺少源版本依据时直接报告缺项。

## 三、复用已有工具

优先使用实际已经提供的工具，调用前检查当前路径及帮助说明；各工具从配置的 `tools` 字段取工作区相对路径。依赖来源和版本由 `github_inputs.json` 固定。

### 1. 上下文查找

蒋逸舟week7中的真实入口为：

```text
.deps/context/week7/context-lookup/context_tool.py
```

仅在现有完整源码及上下文不足时，由你调用：

```powershell
python <实际context_tool.py路径> --project <同版本Java项目根> --target <选中测试文件或完整类型名> --output <项目外的新上下文目录>
```

需要限制源码范围时使用该工具已有的`--source-root`；资源根可用`--resource-root`。读取生成的JSON和Markdown中的实际代码、来源、`related_members`、`unresolved`和`project_issues`。查找失败或达到上限时报告缺口，不伪造工具结果。

不生成`selection.json`。无需提前为全仓库每个方法制作上下文。上下文工具不会为你挑选转换规则、组合项目约定或生成译文；这部分由本任务读取已提供材料完成。

### 2. 公共材料与规则

公共材料工具通过 `tools.public_materials_tool` 定位。示例中指向 `.deps/materials/code/Translate/Project Agreement and Public Materials Generation Tool/pmtool.py`。已有`project_materials.json/.md`时优先读取，不重新扫描和生成整套公共材料。若确有证据缺口，可在已配置的工具目录用其`query/show`读取现有索引；需要重新生成公共材料且配置未提供时记录缺失，不自行建立新的映射研究任务。

规则应按真实ID、适用条件和版本引用；项目特有名称及业务约束以已确认项目材料为准。未知的框架表达不能仅凭类似代码猜造。现有例子若未编译验证，不当作已验证规则。

### 3. 骨架交接

蔡俊杰week8的检查版`member_mapping.json`是记录数组，实际字段包括：

```text
source_members_file / source_member_id / source_location
target_file / target_member / target_line / fill_slot / source_initializer
```

`fill_slot=body`表示填方法体，`fill_slot=initializer`表示填字段初始化。原Java骨架位置可能名为`java_skeleton_location`；规则版`member-map.json`使用`source_skeleton_location`，并可能附带role、disabled、flattened_from、target_declaration等字段。沿用真实字段，不假定已有统一的其他结构。

规则版输出的`diagnostics.json`也应读取。上游出现阻断性诊断时，不能仅看到`.cj`文件存在就认为骨架有效。

现有`check_skeleton.py`检查两份固定样例的骨架声明和`SKELETON_PLACEHOLDER`，不是通用译文检查器；不要用它验证已填充的完整代码，也不要覆盖原映射。

## 四、组织整体翻译所需材料

在生成代码前，对整个选中类形成一致理解：

- 每条测试执行前，哪些字段、构造、准备方法和资源建立初始状态。
- 辅助方法改变了什么状态，是否含断言、异常检查或清理逻辑。
- 测试按什么顺序调用哪些目标接口，观察的是哪个对象。
- 所有断言检查的条件、对象、预期值、异常类型和范围是什么。
- 失败后哪些语句仍应执行，哪些应停止；清理逻辑在什么情况下执行。
- 已有公共设施负责什么，本次需要填充或新增什么。

只组合当前类相关的规则、项目材料和样例上下文，不把整个仓库、所有规则或不相关的参考译文直接塞入输入。测试类本身必须完整读取；材料过长时分批读取同一冻结版本，并记录已读范围，不能静默截断或遗漏剩余方法后声明整体完成。

对影响测试含义的未解决项先补查。可以通过实际文件搜索、定义读取和上下文工具取得依据；无法解决时记入受阻成员。不要生成另一份等待用户填写的片段选择文件。

## 五、填充完整仓颉测试

以已有仓颉骨架为结构约束，在输出副本中一次形成完整测试类及必要测试辅助逻辑。

1. 保留目标包、测试类和已映射成员名称、签名、可见性及生命周期组织。声明确需调整才能保真时，须依据明确规则记录原因与映射变化；关键接口不确定时受阻，不自行设计替代业务接口。
2. 填充所有映射的方法体、构造/准备/清理逻辑及字段初始化槽。字段初值属于测试逻辑，不能因为它没有方法体而漏掉。
3. 保留测试输入、操作顺序、检查对象、全部断言、异常类型及其包围范围，以及辅助方法内的中间断言。不能通过常量返回、删除检查、放宽条件、跳过测试或直接比较预置结果来完成任务。
4. Java断言失败后的控制流应按适用规则保留。不能只因仓颉断言宏表达相似，就忽略软/硬失败、异常捕获和后续调用的差异。
5. 只生成必要的测试辅助代码。不重新实现已有被测业务，不修改目标业务以配合测试，不把业务算法复制进测试来产生预期答案。
6. 资源路径、文件字节、编码和加载约定保持一致。必要资源复制到输出约定位置并记录来源，不以空文件或合成样本代替原测试资源。
7. 源注解、参数化/动态测试、继承或mock机制超出已确认骨架与规则范围时明确报告，不将它们随意简化为普通测试或减少用例。
8. `SKELETON_PLACEHOLDER`、占位异常、TODO空实现和未绑定初始化必须逐项处理。`Option/None`若是上游字段槽，须按真实目标类型与初始化约定填写；如果无法合法替换，保持该成员受阻，不能通过强制解包None或默认空对象掩盖问题。源代码本来使用的合法null/None不作为残留占位误报。

如果某个成员缺少关键材料，可以在`draft/`保存明确标记的未完成候选，结果记为PARTIAL或BLOCKED；不得将含占位的文件放入`translated/`并标为完成。某个成员受阻不应被从源成员清单中删除。

## 六、固定输出

所有文件写入本次新输出目录：

```text
<output>/
  translated/                 已完整填充的.cj测试及必要辅助代码，保持约定相对布局
  resources/                  实际需要复制的测试资源（有需要时）
  draft/                      明确未完成的候选（有受阻成员时）
  input_manifest.json         本轮实际输入、版本与摘要
  translation_result.json     成员处理结果、生成文件、规则依据和缺项
  checks.json                 实际做过的检查与结果
  report.md                   范围、产物、结果和后续交接说明
```

成员对应表保留为输入。翻译后记录新的文件位置、目标成员和行号；如确需派生映射，另存`member_mapping.resolved.json`并记录来源，不回写上游文件。不要输出片段路线的translation_units.json或逐单元状态循环。

`translation_result.json`使用以下结构，示意值必须替换为真实内容；空列表只表示实际没有该类条目，不能替代未处理内容：

```json
{
  "task_id": "本轮标识",
  "mode": "whole",
  "status": "COMPLETE或PARTIAL或BLOCKED",
  "selected_classes": ["完整源测试类型"],
  "outputs": [
    {"path": "translated/实际文件.cj", "sha256": "实际摘要", "kind": "test"}
  ],
  "members": [
    {
      "source_members_file": "实际成员表",
      "source_member_id": "从成员表复制的原ID",
      "source_role": "原角色",
      "status": "TRANSLATED或REUSED或BLOCKED",
      "targets": [
        {"file": "translated/实际文件.cj", "member": "实际目标成员", "line": 1, "fill_slot": "body或initializer或declaration"}
      ],
      "evidence": [
        {"kind": "rule或project_material或context或source", "path": "实际文件", "id_or_location": "真实ID或位置"}
      ],
      "reason": "处理方式或受阻原因"
    }
  ],
  "resources": [],
  "mapping_changes": [],
  "unresolved": [],
  "verification": {"compile": "NOT_RUN", "execution": "NOT_RUN"}
}
```

每个范围内源成员必须出现一次，多个目标位置合并在targets中。REUSED须有真实目标位置和依据；BLOCKED须解释缺口，目标未生成时targets可空。新增目标辅助成员单独记录来源及必要性，不伪造源成员ID。源材料明确排除的成员另在report中列出排除依据，不擅自增加排除项。

`checks.json`每项至少包含检查名、PASS/FAIL/NOT_RUN、检查对象和证据。检查未经执行不得写PASS；如调用了程序，记录命令、工作目录、退出状态和日志路径。

## 七、完成前检查

- **范围与成员**：按members.json和映射逐项核对测试、辅助、生命周期、字段初始化及必要构造；检查遗漏、重复目标和错误复用。测试方法数与实际运行用例数分别记录，参数化测试不能混算。
- **结构与位置**：输出包、导入、声明、成员及映射位置真实存在；输入与受保护的业务文件未被修改。
- **源要求**：逐测试核对准备、调用、观察、全部断言、异常与清理；检查辅助方法中的断言及失败后的执行顺序，断言数量相同不能替代含义核对。
- **占位与资源**：没有未解释的占位、空测试或未绑定字段；资源实际存在，内容与来源摘要一致。
- **规则与接口**：新API调用均有版本、项目接口或实际定义依据。骨架能编译不能证明填充代码或目标业务有效。

以上可由你读取实际文件完成，报告方法和证据；仓库未提供的通用成员检查器不得写成已执行工具。若用临时脚本检查，将脚本及结果保存以便复核；文本/正则检查只支持相应结构观察，不宣称完成仓颉语义解析。

只有配置明确允许且环境/真实业务实现具备时，才运行编译或测试。可复用蒋逸舟week7中的`cangjie_runner.py --config <实际配置> --output <新目录>`，但须使用本轮生成文件及真实业务，不能调用账户参考测试专用入口代替验证本轮结果。预期测试身份从本轮真实目标确定，不硬编码为某个旧样例的数量。

遇到只有声明的compile-support，不写成真实测试验证；SDK缺失、localfix与官方运行库分别记录。不重写业务、源断言或期望清单来消除失败。未经运行，compile/execution均保持NOT_RUN；编译、运行通过也不作为语义等价证明。

COMPLETE要求本轮范围内所有成员都已处理、关键缺项已解决、约定的静态/结构检查通过。它只表示整体译文交付完成，运行验证可以按配置为NOT_RUN；完整执行状态必须单独展示。存在受阻成员为PARTIAL；关键源文、骨架、映射或目标接口缺失而无法安全生成时为BLOCKED。

## 八、最后汇报

完成后只给使用者一段简明结果：选中类与实际处理范围、整体状态、输出目录、成员处理数量、真实检查结果，以及仍需补充的关键材料。主产物必须保存为文件，不能只在聊天里粘贴代码。保持正式、清楚的工程表述，不把分析过程或工具自述写成运行结论。
