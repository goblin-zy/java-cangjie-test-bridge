# Java 测试整体翻译提示词

根据本次翻译范围，以完整 Java 测试类为单位，在已有仓颉骨架中填充测试逻辑及必要的测试辅助逻辑。按以下顺序使用前序步骤交付的材料。

## 一、输入材料

由本次翻译的前序步骤交付下列材料。任务要求、完整 Java 源码、`members.json`、仓颉骨架及其成员对应表用于确定翻译范围和填充位置。其余材料按对应步骤是否执行、当前测试是否涉及该依赖来使用。遇到缺项时，注明应由哪个步骤补交、缺少什么文件或内容、影响哪个类或成员。


| 输入文件或材料 | 产生步骤 | 在整体翻译中的用途 |
|---|---|---|
| 本次任务要求，若已采用建议约定则读取 `translation_config.json` | 准备本次翻译输入 | 确定选中测试、排除范围、源码版本、允许修改的文件和允许复用的范例。成员对应表用于定位，任务要求用于定范围。 |
| 原代码与处理后代码的对应记录、改写记录及未处理情况，文件名由预处理环节约定 | 预处理 | 核对进入骨架提取和上下文查找的是同一版源码，识别改写或未处理事项是否影响测试语义。未修改的源码沿用原件。 |
| `original/` 中的完整 Java 文件、`members.json`、`extraction-report.md` | 同一次 Java 骨架提取 | 完整源码用于理解测试逻辑。成员表用于核对成员 ID、角色、方法体和字段初始化。提取报告用于检查诊断与遗漏。该次交付的 `skeleton/` 是 Java 声明骨架，有结构疑问时可对照。 |
| `translation_rules.json` | 通用规则映射 | 按适用条件查找断言、异常和生命周期等转换规则。 |
| `project_materials.json`、`project_materials.md` | 项目约定与公共材料生成的导出结果 | JSON 用于核对接口对应和条目状态，Markdown 用于阅读包、公共测试设施和资源装配约定。两份文件对应同一次导出。 |
| `context_<标识>.json`、`context_<标识>.md` | 上下文查找对本次测试生成的一组结果 | 用 JSON 核对目标测试、来源位置和未解析引用，用 Markdown 阅读同批辅助代码、业务定义和资源内容。 |
| 仓颉骨架 `.cj` 和成员对应表，实际产物为 `member-map.json` 或 `member_mapping.json` | 仓颉骨架生成或骨架检查 | 骨架给出目标声明，对应表把源成员定位到目标方法体或字段初始化位置。若上游交付同批 `diagnostics.json`，用它判断是否存在阻断性问题。若上游另有 `translation_report.json`，用它了解结构适配及待解决项。 |
| 相关 Java 代码、已有仓颉业务及公共代码、构建配置和测试资源 | 准备本次翻译输入 | 在规则、公共材料或上下文不足时，核对源依赖的行为、真实目标签名和资源内容及加载方式。 |

## 二、处理步骤

### 1. 核对范围和版本

按任务要求确定完整测试类、排除范围和允许复用的目标代码。核对 `original/`、`members.json`、仓颉骨架、成员对应表和上下文是否属于同一批源码。根据提取报告、预处理记录和骨架诊断，列出影响翻译的缺项及涉及成员。

### 2. 把骨架交接转换为待填清单

按源成员 ID 和目标文件、类、签名定位声明，行号用于辅助查找。遇到上游记录采用下列字段时，按其实际含义处理。其他格式沿用该版映射的字段。

- `mapped` 且 `fill_slot: body`，读取完整源码和成员表中的方法体，填充对应测试、构造、生命周期方法或辅助方法。
- `mapped` 且 `fill_slot: initializer`，对照 `source_initializer`、原始声明和目标类型恢复初始化逻辑，核对初始化顺序及后续读取方式。
- `mapped` 且 `fill_slot: null`，核对声明及其现有内容，记录无需填充的依据。
- `reused`，核对目标定义、调用方式和复用限制，保留实际定义的引用。
- `blocked`，检查已有上下文和允许读取的定义能否补足依据。仍受阻时，保留原成员 ID，记录缺项及影响。
- 一对多映射逐个目标位置核对。新增辅助声明按其关联成员和引入原因处理。上游若交付 `translation_report.json`，读取其中的结构适配和未解决项。

### 3. 按完整测试类梳理行为

从完整 Java 源码梳理每条测试的准备、调用、检查和清理，跟进辅助方法中的断言。按需用上下文定位继承成员、类外调用和资源原件。参数化测试核对数据来源和用例范围，继承测试核对生命周期顺序，禁用测试核对禁用条件。

### 4. 确定写法并填充

依据规则的适用条件转换断言、异常和控制流，结合项目材料和真实目标定义确认业务调用及公共设施。在骨架副本中填充相应位置，保留数据、调用顺序、检查对象、全部断言、异常类型及捕获范围。确需调整声明时记录新旧对应和依据。关键语义无法确认时，将受影响的完整类标为受阻。

### 5. 核对并交接

对照源成员逐项检查覆盖、复用和受阻情况。检查完整译文中的占位残留、资源路径和目标测试标识。按实际发现约定记录已知预期标识，尚未确认的列为待核验。将完整类及必要资源交给验证环节，编译和运行状态由验证环节记录。

## 三、输出文件

| 输出 | 来源与内容 | 后续用途 |
|---|---|---|
| 完整仓颉测试 `.cj` 及必要的辅助源码 | 从仓颉骨架填充生成，按目标项目测试布局保存。 | 供后续与实际目标业务源码一起编译和运行。 |
| 必要测试资源 | 来自原测试实际依赖的文件或任务指定的目标资源。需要随译文交接时保存，能直接复用时记录引用。 | 供验证环节按目标项目约定装配。 |
| 翻译交接记录，文件名由流程约定 | 根据本次翻译和核对结果整理。逐类记录输入来源、生成文件、预期测试标识、完成或受阻状态、成员对应变化及未解决事项。 | 供验证环节定位译文和资源、核对预期测试并追踪缺项。 |
